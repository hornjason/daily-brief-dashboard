# ADR-008: Supportable Daily Scrape — Batch Rotation Strategy

**Date:** 2026-04-01
**Status:** Accepted
**Decided by:** Jason Horn

## Context

Supportable APEX must use `PARALLEL_PAGES=1` (session contention constraint). At 22 customers, a full run takes ~33 minutes. At 200 customers (projected scale), a full daily scrape would take 5+ hours — unacceptable for a 7am scheduled job.

Two options were analyzed:
- **Option A (Incremental):** Only scrape customers whose data is older than a threshold. Risk: customers who stop updating never get re-scraped.
- **Option B (Batch rotation):** Split customers into N groups, scrape one group per day, rotating. Every customer refreshed within N days.

## Decision

**Option B — Batch rotation.** 3 groups × ~67 customers per day. Rotating by modulo of a persistent `batchIndex` stored in `data/config/batch-state.json`.

## Consequences

- Runtime is predictable (~65 min/day at 200 customers) regardless of total count
- Every customer refreshed within a 3-day window
- `batchIndex` must survive container restarts — stored in `data/config/` (bind-mounted volume)
- Initial full load (BKL-M44) is excluded from batching — it runs to completion with no time-box
- Adding `scheduleSupportableSync()` to background-scheduler.ts does NOT increase parallelism; PARALLEL_PAGES=1 constraint is unchanged and enforced by the mutex inside `runSupportableDiscoverAndScrape`

## Batch Group Formula

```
group 0: customers[0], customers[3], customers[6], ...  (indices where i % 3 === 0)
group 1: customers[1], customers[4], customers[7], ...  (indices where i % 3 === 1)
group 2: customers[2], customers[5], customers[8], ...  (indices where i % 3 === 2)
```

`batchIndex` starts at 0, increments after each run: 0 → 1 → 2 → 0 → ...
