# ADR-037: Post-Upgrade Data Freshness and Self-Healing System

**Status:** Accepted
**Date:** 2026-06-10
**Deciders:** Serena Blackwood (architecture), Rayford (DA)
**Validated by:** 4 council debates

## Context

When a new container image ships with improved extraction logic, updated prompts, or bug fixes, deployed instances continue serving stale cached data until individual module TTLs expire -- up to 30 days for some modules. Users receive no benefit from code improvements during this window. Three concrete failures drove this decision:

1. **Silent Gemini failures persisted as fresh.** Red Hat org policy blocked `gemini-2.5-flash`. 90+ Gemini calls failed silently. The tech-stack module cached empty extraction results, and TTL-based `ensureFresh()` treated those empty caches as "fresh" because the file existed and was within TTL. Users saw blank tech stack sections for days.

2. **No upgrade awareness.** The system has no concept of "the code that produced this cache is different from the code running now." `ensureFresh()` checks `mtime` vs `cacheTtlMs` -- it has no `codeVersion` dimension. A module fix ships, but cached data generated by the buggy version persists until TTL expiry.

3. **No push mechanism.** There is no way for a deployer to say "this upgrade includes a critical fix -- re-extract everything." The only path is waiting for TTL expiry or manually hitting individual module refresh endpoints one at a time.

The system already has two shipped layers that handle structural problems at startup (entrypoint forced migrations and startup health probes). What is missing is the third layer: awareness that cached data was produced by a different build and should be refreshed.

### Existing Layers (shipped)

**Layer 1 -- Entrypoint Forced Migrations (entrypoint.sh, #746):** Shell-level overrides that run before Node starts. Currently migrates `GEMINI_MODEL=gemini-2.5-flash` to `gemini-2.5-pro` when org policy blocks flash models. Extensible: add new `if` blocks when vendor or org policy changes break existing configs.

**Layer 2 -- Startup Health Probes (startup-health-probe.ts, #746):** Node-level diagnostics that run at early boot via `runHealthProbes()`. Three built-in probes: `gemini-model` (validates model config, auto-heals), `stale-empty-caches` (deletes empty tech-stack cache files that represent failed extractions), `google-auth` (validates Gemini token acquisition). Extensible via `registerProbe()`. Results served at `GET /api/admin/health`. Probes answer "can we serve traffic?" -- they do NOT answer "is data current?"

### What is missing

Layer 3 -- Post-Upgrade Freshness: awareness that cached data was produced by a previous build, visibility into staleness, and user controls to trigger refresh. Six features (F1-F6) compose this layer.

## Decision

### F1: BUILD_HASH Upgrade Detection

At image build time, the Dockerfile writes a `BUILD_HASH` file into the image at `/app/BUILD_HASH`. The file contains a JSON object:

```json
{
  "gitSha": "abc1234",
  "timestamp": "2026-06-10T14:30:00Z",
  "imageTag": "v2.1.0"
}
```

On startup (in `server.ts`, after health probes complete), the app reads `/app/BUILD_HASH` and compares it against `data/cache/.last-build-hash`. If the files differ (or `.last-build-hash` does not exist), an upgrade is detected:

1. Write the current BUILD_HASH to `data/cache/.last-build-hash`
2. Set `upgradeDetected = true` in a module-level flag
3. Kick off `refreshAllModules()` as a background task (non-blocking -- the server starts accepting requests immediately)
4. Log: `[startup] Upgrade detected (old: <prev-sha> -> new: <new-sha>). Background refresh started.`

If the hashes match, no action is taken. Cold boot (no `.last-build-hash`) is treated as an upgrade to ensure first-run instances get fresh data.

**Build integration:** The Dockerfile appends a `RUN` step:

```dockerfile
RUN echo "{\"gitSha\": \"$(git rev-parse --short HEAD 2>/dev/null || echo 'unknown')\", \"timestamp\": \"$(date -u +%Y-%m-%dT%H:%M:%SZ)\", \"imageTag\": \"${IMAGE_TAG:-dev}\"}" > /app/BUILD_HASH
```

### F2: refreshAllModules (Two-Tier Execution)

A new function `refreshAllModules()` in `refresh-engine.ts` replaces the limited `refreshAll()` (which only covers subscriptions + CCSP). It processes all 31 registered modules in two tiers:

**Fast batch (parallel, ~30s total):**
Modules that do NOT call Gemini. These are I/O-bound (Drive reads, HTTP fetches, file parsing) and safe to run concurrently:
- subscriptions, ccsp, pipeline, cases, emails, ecosystem-catalog, partner-catalog, rh-product-catalog, rss, events, docs, value-maps, solution-intelligence, saleshub-content, saleshub, rh-discovery, domain-waterfall, mergers-acquisitions, recommended-actions, product-lifecycle, product-feature-radar, product-release-radar, news-radar, account-team

All fast-batch modules run via `Promise.allSettled()`. Individual failures are logged but do not block other modules.

**Gemini queue (sequential, 15s pause between calls, 5-min total cap):**
Modules that call Gemini for extraction. Sequential execution prevents rate-limit cascading:
- cloud-marketplace, competitive-intel, tech-stack, intelligence, customer-product-intel

Each Gemini module gets a 60s individual timeout. If the 5-minute cap is reached, remaining modules are flagged as `skipped-timeout` in the refresh manifest (not silently dropped). Skipped modules will be picked up by the next `ensureFresh()` call when a user views that customer.

**Engine-level mutex:** An in-memory boolean (`_refreshAllRunning`) prevents concurrent `refreshAllModules()` invocations. If a second call arrives while the first is running, it returns immediately with the current progress. This mutex is separate from the existing per-module `ensureFresh()` mutex -- `ensureFresh()` for a specific module will wait if that module is currently being refreshed by `refreshAllModules()`, but other module `ensureFresh()` calls proceed independently.

**NODE_ROLE awareness:** When `NODE_ROLE` is unset (hero installs), L4-only modules (those requiring browser scraping) are skipped. The module registry already tracks scope; `refreshAllModules()` reads it.

**Progress tracking:** A `refresh-manifest.json` file in `data/cache/` records:

```json
{
  "startedAt": "2026-06-10T14:30:05Z",
  "trigger": "upgrade",
  "totalModules": 31,
  "completed": 18,
  "failed": 1,
  "skipped": 2,
  "inProgress": "competitive-intel",
  "modules": {
    "subscriptions": { "status": "done", "durationMs": 1200 },
    "tech-stack": { "status": "skipped-timeout", "reason": "5-min cap reached" }
  }
}
```

This file is read by the admin API and the upgrade banner (F6).

### F3: Heartbeat Staleness Flagging

The existing 15-minute heartbeat tick (in `background-scheduler.ts`) gains a staleness check pass. For each registered module that declares `cacheTtlMs`:

1. Read the module's primary cache file mtime
2. Compare against `cacheTtlMs`
3. If `mtime + cacheTtlMs < now`: flag the module as `stale` in an in-memory staleness map
4. If `mtime + (cacheTtlMs * 0.75) < now`: flag as `expiring-soon`

The heartbeat does NOT auto-refresh stale modules. It flags only. Rationale: Gemini modules cost money and block the heartbeat tick for 30-60s each. Auto-refresh in the heartbeat was explicitly rejected in council debate 2 because it blocks the tick for the entire duration.

**Boundary with Layer 2 probes:** Probes handle structural corruption (empty files, invalid JSON, missing auth). Heartbeat handles temporal staleness (valid data that is old). A module can be structurally healthy (probe passes) but temporally stale (heartbeat flags it).

**cacheTtlMs becomes a soft requirement:** Modules that produce signals SHOULD declare `cacheTtlMs`. Modules without it are invisible to heartbeat staleness checks and appear as "unknown freshness" in the admin panel. This is not enforced at compile time (the field remains optional in the interface) but IS enforced by the architecture compliance test as a warning for signal-producing modules.

### F4: Admin TTL/Age/Version Visibility

The existing admin Data Sources panel (`/admin` route, Data Sources tab) gains per-module freshness metadata:

| Column | Source | Display |
|--------|--------|---------|
| Last Refreshed | `recordOutcome()` timestamp | Relative time ("2h ago", "3d ago") |
| TTL | Module's `cacheTtlMs` | Human duration ("4h", "7d") |
| Time Until Expiry | `cacheTtlMs - (now - lastRefreshed)` | Countdown or "Expired" |
| Build Version | `BUILD_HASH.gitSha` at time of last refresh | Short SHA ("abc1234") |

**Color coding:**
- Green: within TTL (more than 25% remaining)
- Amber: within TTL but less than 25% remaining (`expiring-soon`)
- Red: TTL expired (`stale`)
- Gray: no `cacheTtlMs` declared (unknown freshness)

**API endpoint:** `GET /api/admin/freshness` returns the staleness map as JSON. The admin React component polls this on a 30s interval when the Data Sources tab is visible.

### F5: Refresh All + Refresh This Customer Buttons

**Refresh All (admin panel):**
- Button at the top of the Data Sources tab
- Calls `POST /api/admin/refresh-all`
- Server invokes `refreshAllModules()` with `trigger: 'manual'`
- Button shows spinner + progress text ("12/31 modules... ~3 min remaining")
- Cancel button sends `POST /api/admin/refresh-all/cancel` which sets a cancellation flag checked between module refreshes
- Disabled while `_refreshAllRunning` is true (shows "Refresh in progress...")

**Refresh This Customer (customer detail page):**
- Button in the customer page header, next to the customer name
- Calls `POST /api/customer/:slug/refresh-all`
- Server calls `ensureFresh()` on all modules registered for that customer, with `force: true` to bypass TTL checks
- Shows spinner + per-module progress
- This is distinct from `refreshAllModules()` -- it refreshes one customer's data across all modules, not all modules for all customers

### F6: Upgrade Banner + Per-Section Staleness

**Upgrade banner:**
- Displayed on the main dashboard page when `upgradeDetected` is true AND `refreshAllModules()` is still running
- Reads progress from `refresh-manifest.json` via `GET /api/admin/refresh-all/status`
- Text: "Data refresh in progress -- 12/31 modules updated, approximately 8 minutes remaining"
- Dismisses automatically when refresh completes
- Dismissible manually (sets a session cookie; does not suppress the refresh)

**Per-section staleness indicators (customer detail page):**
- Each data section (Tech Stack, Cases, Pipeline, etc.) shows a timestamp: "Updated 2h ago"
- If the module is currently being refreshed: "Refreshing..."
- If the module's data is stale (TTL expired): timestamp shown in amber with "(stale)" suffix
- Timestamps come from `recordOutcome()` data already tracked by the registry

## Consequences

### Positive

- **Immediate value from upgrades.** Code fixes propagate to cached data within minutes of container restart, not days.
- **Visibility into data currency.** Users can see exactly how fresh each module's data is and take action.
- **Self-healing for silent failures.** Empty caches from Gemini failures (Layer 2 probe) combined with code-version-aware refresh (Layer 3) means failed extractions are both cleaned up and re-attempted.
- **Cost-controlled.** Gemini modules are sequential with a 5-minute cap. A full refresh costs roughly $2-5 depending on customer count. Manual refresh is user-initiated, not automatic.
- **Extensible.** New modules automatically participate -- `refreshAllModules()` reads from the registry. No hardcoded lists.

### Negative

- **First-boot delay.** Cold boot triggers a full background refresh. The server is responsive immediately, but data sections show "Refreshing..." for 3-8 minutes until the Gemini queue completes.
- **Gemini cost on every deploy.** Each `make rebuild` that changes the git SHA triggers a full refresh. Frequent deploys during development could accumulate costs. Mitigation: delta cache (`deltaKey` in `callGemini()`) already hashes prompt input including `IMAGE_TAG` -- if the actual extraction prompt hasn't changed, Gemini is not called.
- **Manifest file I/O.** `refresh-manifest.json` is written on every module completion during `refreshAllModules()`. On a 31-module refresh this means 31 writes. Acceptable for a single-user app; would need buffering at scale.

### Risks

- **Race between upgrade refresh and user-initiated ensureFresh.** Mitigated by per-module mutex in the registry. Both paths acquire the same lock before refreshing a module.
- **5-minute cap may skip important Gemini modules.** Mitigated by ordering Gemini modules by business value (cloud-marketplace first, customer-product-intel last). Skipped modules are flagged, not silently dropped, and will be refreshed on next `ensureFresh()` call.

## Alternatives Considered

### 1. Auto-refresh in heartbeat tick

**Rejected.** The heartbeat runs every 15 minutes. If it auto-refreshed stale Gemini modules, it would block the tick for 30-60s per module. With 5 Gemini modules, that is up to 5 minutes of blocked heartbeat -- during which staleness checks, scheduler status updates, and other heartbeat work are delayed. The heartbeat should flag, not fix.

### 2. Single global version hash for all modules

**Rejected.** A single hash means every code change invalidates every cache. A typo fix in `news-radar` would trigger re-extraction of `tech-stack` (expensive Gemini call) even though tech-stack code is unchanged. Per-module `codeVersion` was considered but deferred -- the `BUILD_HASH` approach (refresh everything on upgrade, let delta cache skip unchanged modules) achieves the same result with less complexity. The delta cache in `callGemini()` already handles the "prompt unchanged" case by hashing input and returning cached results.

### 3. Eager bulk purge on deploy

**Rejected.** Deleting all caches on deploy means the app starts with zero data. Every page load triggers cold extraction. For 15 customers with 31 modules each, that is 465 extraction calls in the first few minutes -- many of them Gemini calls. The lazy approach (serve stale data while refreshing in background) provides a better user experience: the dashboard is immediately usable with old data, and data updates incrementally as modules complete.

### 4. Per-module codeVersion in FeatureModule interface

**Deferred.** Adding a `codeVersion: string` field to each module (bumped when module logic changes) would enable targeted invalidation -- only refresh modules whose code actually changed. This is the theoretically optimal approach but adds developer burden (must remember to bump the version) and is error-prone (forget to bump = stale data persists). The `BUILD_HASH` + delta cache combination achieves 90% of the benefit with zero developer burden. Per-module `codeVersion` can be added later if the cost of unnecessary Gemini calls on deploy becomes material.

## PRINCIPLES.md Update

This ADR creates three mandatory updates to PRINCIPLES.md:

### 1. New pre-flight question (Q17)

> **17. Does this module declare `cacheTtlMs` for heartbeat visibility?** (ADR-037) Every module that produces cached data SHOULD declare `cacheTtlMs` so the heartbeat staleness checker can flag expired data and the admin panel can show freshness status. Modules without `cacheTtlMs` appear as "unknown freshness" in the admin panel -- users cannot diagnose or act on stale data. Architecture compliance test warns for signal-producing modules missing this field.

### 2. New anti-pattern

> - Caching empty extraction results as "fresh" (ADR-037) -- when a Gemini extraction or API call fails and returns empty/null results, the module must NOT write the empty result to cache. Empty results should either be skipped (preserve previous cache) or written with a `failed: true` marker that `ensureFresh()` treats as expired regardless of TTL. The Layer 2 `stale-empty-caches` probe catches these retroactively, but modules should prevent them proactively.

### 3. New contract section: Three-Layer Data Lifecycle

> ## Three-Layer Data Lifecycle Contract (ADR-037)
>
> Data correctness across container upgrades is maintained by three layers, each with a distinct responsibility:
>
> | Layer | Runs at | Responsibility | Scope |
> |-------|---------|---------------|-------|
> | 1. Entrypoint Forced Migrations | Shell, before Node | Override known-bad env vars | Environment config |
> | 2. Startup Health Probes | Node, early boot | Detect and heal structural problems (empty caches, bad auth, blocked models) | Data structure |
> | 3. Post-Upgrade Freshness | Node, after probes | Detect build change, refresh stale data in background, surface staleness to user | Data currency |
>
> **Layer boundaries are strict:**
> - Probes (Layer 2) must NOT refresh data -- they validate structure and heal corruption
> - Heartbeat staleness (Layer 3) must NOT auto-refresh -- it flags only
> - `refreshAllModules()` (Layer 3) is triggered by upgrade detection or manual user action only
> - `ensureFresh()` remains the per-request lazy refresh path -- it is NOT part of this lifecycle
