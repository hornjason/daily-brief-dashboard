# ADR-007 — Bun as Runtime

**Status:** Accepted
**Date:** 2026-04-01

---

## Context

DailyBriefDashboard runs a persistent server process inside a Podman container. The server handles:
- HTTP API (Hono framework)
- Playwright-based browser scrapers (Chromium)
- Background refresh timers for Google Sheets data
- Long-lived in-memory state (session flags, cache, mutex guards)

A runtime had to be chosen. The candidates at project start were **Bun**, **Node.js + tsx**, and **Deno**.

---

## Decision

**Bun** was chosen as the runtime.

TypeScript files are executed directly via `bun run src/server.ts` with zero transpilation step. The Hono framework is idiomatic in Bun. All dependencies (`@playwright/test`, Google APIs, Hono) work under Bun without modification.

---

## Rationale

1. **Zero build step** — Bun runs `.ts` files natively. No `tsc` compile-then-run cycle; the container starts with `bun run src/server.ts` directly. This simplifies the Containerfile and eliminates a class of "compiled code is stale" bugs.

2. **Speed** — Bun's startup and module resolution are measurably faster than Node + tsx. Not critical at this scale, but reduces container cold-start time on `make rebuild`.

3. **Native fetch / Web APIs** — Bun ships `fetch`, `FormData`, `AbortController` natively without polyfills.

4. **Framework alignment** — Hono is built for Bun/Cloudflare Workers first. The ergonomics (`c.req.json()`, streaming, middleware) are cleaner under Bun than under Node.

5. **Low migration cost** — The project started in Bun. Migrating to Node + tsx now would require verifying every import, replacing `Bun.file` calls, and retesting all scrapers. The risk/reward ratio is poor.

---

## Known Limitation — Long-Interval Timer Unreliability

`setInterval` with intervals greater than approximately 1 hour is **not reliably fired** in Bun. The interval callback may be delayed arbitrarily or skipped entirely.

**Workaround in use (do not remove):**

The RH scrape background timer uses a 15-minute heartbeat tick instead of a single long-interval `setInterval`. Each tick reads the elapsed time since the last scrape and only fires the scrape when the configured interval has passed:

```typescript
const RH_SCRAPE_TICK_MS = 15 * 60 * 1000  // reliable in Bun

setInterval(() => {
  const intervalMs = getRefreshIntervals().rhScrape * 60 * 1000
  const elapsed = Date.now() - lastScrapeMs
  if (elapsed >= intervalMs) {
    runRhScrapeWithState()
  }
}, RH_SCRAPE_TICK_MS)
```

The subscriptions and CCSP timers use direct `setInterval` with their configured intervals (default 240min and 1440min). These are also potentially affected by the Bun timer bug. If those timers miss their scheduled fires in production, apply the same heartbeat pattern.

**Alternative not taken — system cron:** Using `cron` inside the container was considered. Cron would be reliable for wall-clock scheduling. It was rejected because: (a) it requires an additional daemon in the container, (b) scheduled commands would need to hit the HTTP API rather than calling refresh functions directly, adding a network hop and error surface, (c) the pipeline 2am sync already uses a correct timezone-aware `setTimeout` reschedule loop that handles EST/EDT transitions correctly — cron would require a separate TZ configuration. The heartbeat pattern achieves the same reliability without those tradeoffs.

**Alternative not taken — Node.js + tsx:** Node + tsx was considered as a drop-in swap. It was rejected because: (a) Node's `setInterval` long-interval behavior is the same class of issue (JS event loop, same root cause), (b) migration cost without clear benefit, (c) the heartbeat workaround already resolves the reliability concern.

---

## Consequences

- Bun stays as the runtime until a clear defect makes migration necessary.
- All new timers with intervals > 30 minutes MUST use the heartbeat pattern, not a direct long-interval `setInterval`.
- Background scheduler code in `src/background-scheduler.ts` is the authoritative source for all timer implementations.
- If Bun is upgraded, re-test long-interval timer behavior — the limitation may be fixed in newer versions.
