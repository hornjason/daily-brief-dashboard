# ADR-013: AI Intelligence Cache Hierarchy and Fingerprint Design

- **Status:** Accepted
- **Date:** 2026-04-19
- **Related:** ADR-007 (Bun timer reliability), `docs/ai-ingestion-flow.md`, `docs/GEMINI-AUDIT.md`

---

## Context

Brief generation is the most Gemini-heavy code path in the system. A single
brief regeneration can trigger 1 brief-extract call, 1 brief-synthesize call,
and 12+ doc-classify calls, plus L4 intelligence calls if their TTLs have
expired. Without disciplined cache invalidation, every page view risks burning
Gemini tokens on signals that have not changed.

A naive TTL-only cache is insufficient:

- **Too short** (1–4h) — re-generates briefs all day even when no signals
  changed, wasting tokens and money.
- **Too long** (24h+) — misses intra-day signal changes (new email, meeting
  added, case opened) that the user expects the brief to reflect.

The system needs **deterministic cache invalidation based on input
fingerprinting**, not just elapsed time. When the fingerprint matches, the
brief is reused regardless of TTL. When the fingerprint differs, the brief
regenerates regardless of TTL. TTL becomes a backstop, not the primary
invalidation signal.

The cache also needs tier separation. Per-source signals (emails, meetings)
have different freshness needs than per-doc content (which only changes on
Drive `modifiedTime` advance) and derived intelligence (which only changes
when its inputs do). Mixing them creates over-invalidation and waste.

---

## Decision

Implement a **4-tier AI intelligence cache hierarchy** parallel to the data
ingestion L1–L4 layers. Each tier has a single invalidation strategy and a
documented purpose. The brief cache (L1) is keyed by a composite fingerprint
hash, not just slug+date.

## Implementation Details

### Fingerprint composite inputs

The L1 brief fingerprint is a SHA-256 hash over a deterministic JSON
serialization of:

- Sorted `(subject, sender, date)` tuples for in-window emails
- Sorted `(title, attendees, date)` tuples for in-window meetings
- Customer's CCSP tier label
- Customer's dominant pipeline stage (or stage distribution hash)
- Open case count by severity, last-90-days only
- User preferences hash (tone, length, focus)

Sorting is critical — it removes ordering churn from upstream APIs that would
otherwise invalidate the cache without an actual signal change. The 90-day
window on cases prevents stale cases from continually invalidating fingerprints
when nothing has materially changed.

### `ai-events.ts` SSE event schema

All cache and generation activity emits structured events on a server-side
EventEmitter that bridges to `GET /api/ai/events` SSE.

```ts
type AiEvent =
  | { type: 'cache:cold' | 'cache:hit' | 'cache:miss' | 'cache:bypass' | 'cache:stale';
      tier: 'L1' | 'L2' | 'L3' | 'L4';
      key: string;
      customerSlug?: string;
      fingerprint?: string;
      durationMs?: number;
      ts: string;
      meta?: Record<string, unknown>; }
  | { type: 'generation:start' | 'generation:complete' | 'generation:error';
      callSite: string;
      customerSlug?: string;
      durationMs?: number;
      tokensIn?: number;
      tokensOut?: number;
      error?: { code: string; message: string };
      ts: string; }
```

Events are also tee'd to `data/cache/ai-events-{date}.jsonl` for post-hoc
analysis.

### `DISALLOW_GEMINI` behavior

The `callLLM` and `callLLMStructured` helpers honor a `DISALLOW_GEMINI` flag
on their options object (and a process-level env var fallback). When set:

- The helper short-circuits **before** any Gemini network call
- A `generation:error` event with `code: 'DISALLOWED'` is emitted
- The caller receives a typed error indicating the call was suppressed by
  policy

This is used by the test container (port 7776) to guarantee no Gemini spend
during integration runs, and by the `cache:bypass` debug flow when the user
wants to see cache misses without paying for regeneration.

## Consequences

### Positive

- **Brief generation invalidates on signal changes intra-day, not just TTL.**
  A new customer email arriving at 10am triggers the next brief view to pick
  up a fresh fingerprint and regenerate; without fingerprinting this required
  waiting up to 7 days for the TTL.
- **Delta mode reduces Gemini input tokens 80–90% for customers with many
  unchanged docs.** Most customer corpora are stable; delta mode encodes that
  stability in the cache key and skips the redundant Steps 1+2 work.
- **`DISALLOW_GEMINI` enables cost-safe test environments and debug flows.**
  Test container runs cannot accidentally bill production Gemini quota.
- **SSE event bus makes cache behavior observable.** Developers and Jason can
  see live in the dashboard which tiers are hitting and missing without
  re-running with verbose logs.
- **Tier separation prevents cross-invalidation.** A change in CCSP tier no
  longer evicts cached doc content; a Drive doc edit no longer evicts cached
  industry analysis.

### Negative

- **Fingerprint computation has a small fixed cost** (sort + hash) on every
  brief view. Measured at < 5ms for typical customers.
- **Cache key churn risk if fingerprint inputs are added carelessly.** Adding
  a noisy input (e.g., a constantly-changing timestamp) would invalidate the
  cache constantly. Inputs must be deliberately chosen and sorted.
- **Two invalidation paths to reason about** (fingerprint AND TTL). Documented
  here and in `docs/ai-ingestion-flow.md` to keep the model clear.

### Neutral

- The implementation is parallel to but independent of the data-ingestion
  L1–L4 hierarchy. Both use the same vocabulary; mismatches between the two
  must be flagged in code review.
