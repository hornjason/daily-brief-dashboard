# ADR-009: Brief Cache — Content-Hash + 4h TTL Invalidation

**Date:** 2026-04-04
**Status:** Accepted
**Decided by:** Jason Horn

---

## Context

The brief cache previously used a single-condition invalidation strategy: a brief was regenerated only when the backing sheet data was newer than the cached brief (`sheetData.cachedAt > brief.cachedAt`).

This caused a problem: when scrapers ran frequently (e.g. every 15 minutes for RH cases) or when sheet data changed multiple times a day, every sheet sync triggered brief regeneration — incurring Gemini API costs and introducing latency on every customer page load.

Conversely, if the sheet data didn't change for several days, briefs could go stale indefinitely even though email/calendar data (not included in the staleness check) had new content.

---

## Decision

**Two-condition invalidation with 4-hour TTL cap.**

`cache-layer.ts` exports:
```typescript
export const BRIEF_CACHE_TTL_MS = 4 * 60 * 60 * 1000  // 4 hours
```

The brief route (`customer-routes.ts`) regenerates a cached brief when **either** condition is true:
1. Sheet data is newer than the cached brief (`sheetTs > briefTs`)
2. Brief age exceeds TTL (`Date.now() - briefTs >= BRIEF_CACHE_TTL_MS`)

`force=true` query parameter bypasses both conditions and always regenerates.

---

## Consequences

- Briefs regenerate at most once every 4 hours under normal conditions
- Sheet syncs that occur within the 4h window do NOT trigger brief regeneration — reduces Gemini API calls
- Maximum brief staleness is bounded at 4h even if sheet data never changes
- `force=true` (surfaced as a "Force Refresh" button in the UI) provides the escape hatch for immediate regeneration
- Drive-watcher-based invalidation (`invalidateBriefCaches()`) still works — it deletes the cache file entirely, causing the next request to regenerate regardless of TTL
