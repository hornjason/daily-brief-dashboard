# ADR-012: Product Intelligence Hub — Drive Optional, Feature Injection, Cap Expansion

**Date:** 2026-04-06
**Status:** Accepted
**Decided by:** Jason Horn

---

## Context

Three decisions were made during Phase 2 and Phase 3 of the Product Intelligence Hub build that have architectural impact and needed to be captured.

---

## Decision 1: Drive Corpus Is Optional

### Context

The original design (W3-12 §2A) required every product to have a `driveFolderId` configured before the generate route would run. In practice, Jason may add products before Drive folders exist for them, and the release-notes pipeline is independently valuable without Drive content.

### Decision

`driveFolder` on `ProductConfig` is `string | null`. The generate route in `product-intel-routes.ts` does not require `driveFolder` to be set. When null, the Drive ingest step is skipped and synthesis runs on release-notes content only. No error is returned to the caller.

### Consequences

- Products can be activated immediately with release-notes-only synthesis
- Drive content is additive when added later — no rebuild required
- The `POST /api/products/:slug/ingest-drive` endpoint still returns 400 if `driveFolder` is null (ingest has nothing to do)
- No data loss risk: skipping Drive ingest does not delete or overwrite existing feature cache

---

## Decision 2: Feature Radar Injected into Customer Product Intel Prompt

### Context

Phase 3's original brief integration plan (W3-12 §4B) was to inject product intelligence as `<source type="product_intelligence">` XML blocks into `buildXmlSources()` in `customer.ts`. This would have made product features part of the main daily brief.

Descoped reason: the main brief already has a tight token budget across 8+ source types. Injecting product features per matched product would unpredictably expand brief prompts and inflate cost.

### Decision

Product features are injected into `generateCustomerProductIntel()` in `customer-product-intel.ts` only — not into the main brief pipeline. The `generateCustomerProductIntel()` call accepts `productFeatures` (raw feature text, 4000-char cap) and `productFeaturesHash` (SHA-256 of corpus for cache invalidation). Gemini selects the top 3-5 relevant features and returns them as `featureTalkingPoints` on the `CustomerProductIntel` type.

This keeps main brief cost stable. Product talking points are surfaced on the customer detail page (product intel section), not in the brief text itself.

### Consequences

- Main brief generation (`customer.ts`) is not affected by this feature
- `CustomerProductIntel.featureTalkingPoints` is a new field — old cache files without it are treated as stale and regenerated
- Content hash includes `productFeaturesHash` so when the Drive corpus changes, all customer intel for that product is invalidated
- Chat interface (original Phase 3 plan) was also descoped; `POST /api/products/:slug/chat` does not exist

## Decision 3: Account Intel Cap Expansion

### Context

With feature radar injection, the Gemini prompt for `generateCustomerProductIntel()` grew significantly. The previous 2000-char company cap and 1000-char industry cap were too tight once feature context was added — Gemini was truncating the feature block to stay under the input budget.

### Decision

Company content cap: 2000 → 6000 chars
Industry content cap: 1000 → 2000 chars

These caps apply in `customer-product-intel.ts` when assembling the prompt context. The feature block has its own 4000-char cap (separate from company/industry).

### Consequences

- Average input tokens per `generateCustomerProductIntel()` call increases ~40-60%
- Cost per call estimated to increase from ~$0.002 to ~$0.003 at Gemini 2.5 Flash rates
- All calls are recorded via `recordGeminiUsage()` with callType `product-intel-*`
- Content hash changes invalidate existing customer intel cache — expect one-time re-generation after deploy

## Decision 4: 7-Product Bootstrap Scaffold (First AE Only)

### Context

The setup wizard scaffolds a shared `Product Intelligence/` Drive folder with subfolders per product. With 7 products (up from 3), the scaffold tree changed. More importantly, for second+ AEs, the Product Intelligence folder already exists — recreating it is wasteful and may cause naming conflicts.

### Decision

The Product Intelligence scaffold in `SetupPage.tsx` is gated on `knownAes.length === 0`. The wizard shows the 7-product folder tree only on the first AE setup. Subsequent AEs see only their own AE folder structure. The bootstrap orchestrator itself remains idempotent — if the folder exists it reuses it — but the wizard UI no longer suggests it will be created.

### Consequences

- First AE bootstrap creates: rhel, ocp, ocp-virt, aap, rhel-ai, rh-ai-inference, rhoai subfolders
- Subsequent AE bootstraps skip the Product Intelligence scaffold entirely
- If a new product is added later, the Drive subfolder must be created manually or via `POST /api/products/scaffold-drive`
