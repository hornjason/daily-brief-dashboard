# ADR-004: Sequential execution for background refresh operations

**Date:** 2026-03-31
**Status:** Accepted

## Context

DailyBriefDashboard performs several background refresh operations that fetch data from external services (Google Sheets, Salesforce, Red Hat Supportable, CCSP/Tableau) and write the results to shared cache files and Google Sheets.

Two design questions arose during the M02 refactor of `server.ts`:

1. **Sequential vs parallel** for multi-customer refresh within a single refresh pass
2. **Timer granularity** for recurring background jobs in a Bun container process

## Decision

### Sequential execution within refresh passes

All multi-customer refresh loops (`refreshSubscriptions`, `refreshCCSP`, `refreshAll`) iterate customers sequentially — one customer at a time — rather than in parallel batches.

This was the existing pattern in `server.ts` before extraction and is intentional for three reasons:

1. **Google Sheets API quota**: The Sheets API has a per-project rate limit (~60 requests/min read, ~10 requests/sec write). With 22 customers each requiring multiple Sheets reads, parallel execution exhausts the quota before most customers complete. Sequential execution with the `withQuotaRetry` wrapper keeps request rates within quota.
2. **Shared browser context**: CCSP scraping shares one Playwright `BrowserContext` across all scrapers (see ARCHITECTURE.md §1 — Shared browser context is intentional for Tableau SSO). Concurrent scrape operations on the same context cause session state collisions.
3. **In-memory mutex flags**: The single-threaded Bun process uses boolean mutex flags (`_rhScrapeRunning`, `ccspScrapeRunning`, etc.) to prevent overlapping scrape runs. Sequential execution in refresh passes ensures these are respected without needing async coordination.

### Pipeline sync timer — DST-safe implementation

The pipeline daily sync (scheduled at 2am ET to match Salesforce report generation at 1am ET) uses a recursive `setTimeout` loop rather than `setInterval`. The implementation uses `Intl.DateTimeFormat` to derive the current ET offset dynamically:

```typescript
const etOffsetMs = _now.getTime() - etAsIfUtcMs  // derives EST (UTC-5) or EDT (UTC-4) correctly
```

This correctly handles Daylight Saving Time transitions without hardcoding UTC offsets:
- **Spring forward** (March): At 2am, clocks jump to 3am EDT. The computed target is 7am UTC (moment of transition), falling to 6am UTC for subsequent days in EDT.
- **Fall back** (November): At 2am EDT, clocks fall back to 1am EST. The first 2am occurrence (6am UTC, EDT) is targeted; after the transition the next day's 2am EST (7am UTC) is used.

### Short-tick scrape scheduler

The RH scraper uses a 15-minute `setInterval` tick rather than a 4-hour interval. Bun's runtime does not reliably fire `setInterval` callbacks with intervals longer than ~1 hour inside container processes. The tick checks elapsed time since last scrape and only triggers when the configured interval has elapsed.

## Consequences

**Positive:**
- Quota exhaustion is avoided — all 22 customers complete each refresh cycle
- DST transitions are handled correctly by the scheduler without manual intervention
- No scraper race conditions from concurrent context access

**Negative:**
- Full subscription refresh for 22 customers takes ~3–5 minutes sequentially. This is acceptable given the 4-hour default refresh interval.
- Pipeline sync fires at most once per day; slight timing drift (seconds) is acceptable.

**Non-issues:**
- The 15-minute tick has negligible CPU impact — each tick completes in <1ms
