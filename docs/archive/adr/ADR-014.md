## ADR-014 — Dual-Transport Architecture for RH Portal Case Refresh

**Status:** Accepted  
**Date:** 2026-04-18  
**Author:** Council debate (Serena, Marcus, Ava, Rook) — Jason Horn (decision)

---

### Context

RH Portal case data is currently fetched via Playwright browser automation — `page.evaluate()` calls to the hydra SOLR API using SSO session cookies (`credentials: 'include'`). This works but has three problems:

1. **Browser dependency on refresh:** Every case data refresh requires an active SSO browser session, keepalive loop, and Playwright overhead — 5-15s per customer vs ~1.1s for a direct HTTP call.
2. **CI/headless blocking:** The Mac Mini CI runner cannot authenticate to RH Portal via SSO, blocking automated release gate testing of the RH scrape path.
3. **Fragility:** SSO session expiry causes silent stale data with no visible failure signal.

Investigation on 2026-04-18 confirmed: `POST /hydra/rest/search/v2/cases` accepts `Authorization: Bearer [token]` from the existing `REDHAT_OFFLINE_TOKEN` offline token exchange (already in `.env`, already implemented in `src/redhat.ts`). Response is identical to the browser-cookie path: same fields, same data, ~1.1s latency.

---

### Decision

Adopt a **dual-transport architecture** for RH Portal case data:

**Bootstrap / Discovery (browser — unchanged):**
- Browser sidebar autocomplete remains the authoritative source for account number discovery
- No SOLR name query is as reliable as the live portal sidebar (handles zero-case accounts, name variants, reseller patterns)
- `discoverAccountNumberByName()` in `rh-scraper.ts` is NOT modified

**Recurring Refresh (Bearer — new):**
- All recurring case refresh calls (manual scrape, scheduled scrape, brief pre-generation) use `fetchCasesViaSolr()` via Bearer token
- No browser page required for refresh after bootstrap
- Implemented behind a `CaseClient` interface with two concrete implementations

**Interface boundary (hard rule):**
- `CaseClient` interface lives in `src/case-client.ts`
- Exactly two implementations: `BearerCaseClient` (refresh) and `BrowserCaseClient` (discovery fallback / DR)
- This cap is permanent — a third implementation signals the abstraction is wrong
- Document in this ADR; enforce in code review

---

### Architecture

```
Bootstrap (once):
  customer name
    → BrowserCaseClient.discoverAccountNumbers()   [sidebar autocomplete, unchanged]
    → customers.json { accountNumbers: [...] }

Recurring refresh:
  customers.json accountNumbers
    → CaseClient.fetchCases(accountNumbers)
        ├── BearerCaseClient (primary)              [fetchCasesViaSolr(), ~1.1s]
        │     ├── getToken() → Bearer exchange
        │     ├── POST /hydra/rest/search/v2/cases
        │     └── on 401 → HealthProbe fires, loud failure, no silent fallback
        └── BrowserCaseClient (DR / fallback)       [page.evaluate, browser session]
              └── invoked only on explicit Bearer failure + manual override
```

---

### Token Hygiene (mandatory before Phase 2 ships)

| Requirement | Implementation |
|---|---|
| Token encrypted at rest | OS keychain or sealed secret (not plain .env long-term) |
| Proactive refresh | Refresh at 70% of token lifetime (~3.5min of 5min window) |
| 401 handling | State machine: alert + dashboard banner + quarantine token — never silent |
| Auth-mode tagging | Every SOLR call tagged with `authMode: 'bearer' \| 'browser'` in logs |
| Audit log | Structured log entry per case fetch: customerName, authMode, durationMs, caseCount |
| Token age telemetry | HealthProbe exposes: authMode, tokenAge, last401, lastRefreshAt |

---

### Regression Guardrails (mandatory — cannot ship without these)

Phase 2 **must not break production case data**. The following gates are required before `make rebuild`:

1. **Golden snapshot test:** Capture current browser-path case output for 3 known customers before any code change. Assert field parity after wiring Bearer.
2. **Field completeness:** Every field currently returned by the browser path must be present in Bearer response: `caseNumber`, `summary`, `status`, `severity`, `accountNumber`, `product`, `createdDate`, `daysOpen`.
3. **401 regression test:** Force token expiry, assert loud failure surfaces (banner + log entry), assert no stale data served silently.
4. **Fallback test:** Disable Bearer path, assert browser fallback runs and returns valid data.
5. **Count parity:** Case count from Bearer must be within ±1 of browser path for same customers (pagination edge case tolerance).
6. **All tests on 7776 before rebuild** — zero exceptions.

---

### Browser Path Retirement

The browser case-fetch path is **intentional DR infrastructure, not technical debt.**

- Red Hat owns the offline token lifecycle. Token policy changes or revocations are outside our control.
- Browser path stays warm: exercised on a quarterly schedule, not deprecated.
- Re-evaluate browser retirement at 90-day checkpoint (2026-07-18): if Bearer has run without incident and SOLR discovery is proven reliable, browser discovery can be considered for retirement with explicit sign-off.
- Hard rule: browser path is never removed without a verified Bearer fallback for every customer segment including resellers.

---

### Consequences

**Positive:**
- Refresh cycle: 5-15s per customer → ~1.1s (5-10x faster)
- Browser keepalive dependency eliminated for refresh
- CI headless testing of case data becomes possible
- Smaller credential attack surface (one token vs Chromium profile on disk)
- Explicit health monitoring replaces implicit SSO session health

**Negative:**
- Two code paths to maintain (bounded by the two-implementation cap)
- Token rotation hygiene required (proactive refresh at 70% lifetime)
- `.env` offline token becomes a crown-jewel secret requiring rotation runbook
